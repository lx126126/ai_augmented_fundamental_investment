# 架构设计文档

> AI 增强基本面投研 · ValueLine 一页研报
> 版本：v2.0（2026-09-02）

## 1. 项目概述

为 A 股标的输出 **ValueLine 风格的一页投研报告**，季度更新。代码通过 GitHub 维护。

**产品定位（2026-09-02 更新）**：本项目的报告是**纯客观的数据工具**——数据加工 + 指标 + 风险检测（排雷），**不含本人观点**（无本人目标价、多空、买卖建议），但**保留第三方机构的多空/评级观点**（客观数据，如实呈现）。核心目的只有一个：**真正帮助自己做投资决策前先排雷**。产品化、商业化、主观分析判断都往后放，先把数据工具打磨好。

核心方法论（作为**分析框架**，而非观点输出）：**格雷厄姆流派（安全边际 / 财务稳健）+ 彼得·林奇六类公司分类**。

---

## 2. 产品定位

### 2.1 报告是什么：纯客观数据工具

一份报告只包含两类内容，全部可自动化生成：

| 类型 | 模块 | 生成方式 |
|------|------|---------|
| 数据加工 | 财务数据（全历史/季度/业务构成/股本）、估值分位、52周区间、机构评级/预测（第三方客观数据，含多空倾向） | 拉取 + 计算，100% 自动化 |
| 风险检测 | Beneish M-Score、现金流背离、应收异常、审计意见（非标一票否决） | 算法计算，100% 自动化 |

### 2.2 报告不包含什么

- **不输出「本人」观点**：无本人目标价、无本人多空判断、无买卖建议。**第三方机构的多空/评级观点照常保留**——它是客观数据，如实呈现，标注「第三方机构观点，非本人建议」。
- **不接商业变现假设**：不设「公开端 / 付费端」分层，不追求引流、转化、赚钱。
- **主观判断只进私有投研日记**（`journal/`，已 gitignore，不进公开产物），只服务自己决策。

### 2.3 为什么这么定位

> 数据工具的护城河在「数据可信 + 风险检测」，不在「我自己的观点」。机构怎么看（多空/评级）是可采集、可校验的客观事实，属于数据加工；我自己怎么看，属于主观判断，只进日记。先把客观数据这一层做扎实，主观分析和商业化都是以后的事。

## 3. 总体架构（四层）

```
数据层   →  分析层   →  报告层
采集·校验·入库  指标·估值·风险检测  一页报告·季度更新
─────────────────────────────────────────────────────
        方法论底座：格雷厄姆流派 + 彼得·林奇六类
```

- **数据层**：多源采集 → 文档解析（PDF 财报结构化抽取）→ 清洗校验 → 入库（parquet + DuckDB 数仓）
- **分析层**：基本面指标、估值分位、林奇六类分类、格雷厄姆质量体检、财务造假检测（排雷）
- **报告层**：ValueLine 一页 HTML 模板 + LLM 文本生成（仅翻译数据，不编观点）+ 季度更新引擎 + 跟踪池管理

## 4. 数据层设计

### 4.1 数据源

| 数据 | 主源 | 备用源 | 自然频率 |
|------|------|--------|---------|
| 财报（利润表/资产负债表/现金流） | AKShare | 东方财富 | 季度披露 |
| 行情 / 估值（股价、52周、PE/PB） | AKShare | mootdx / 腾讯 | 每交易日 |
| 机构评级 / 预测 EPS | AKShare / 东财 | Wind（若有） | 持续更新 |
| 分业务收入构成 | 公司财报 | 东财 | 季度/年度 |
| 股本结构（普通股/优先股） | 财报 | — | 变动时 |

> **文档解析（PDF / HTML 结构化抽取）**：财报与公告的原始形态是 PDF / HTML，需抽取为可用表格——PDF 财报（招股书/年报，含图片型 PDF 与复杂表格、中英文，规则解析）、HTML 公告（巨潮等）。当前已落地：巨潮年报 PDF + pymupdf 表格抽取，作为金标准交叉校验接口数据。此模块对齐岗位的「文档解析」能力，与金融数据方向天然契合。

### 4.2 预计算方案（关键）

「搜索即出报告」要求秒级响应，**不能用户搜索时才实时拉取**（单股全历史拉取需数十秒且限流）。

正确做法：**后台定时预计算 → 入库 → 搜索时直接渲染**。

```
后台定时任务（分层调度）
  财报数据 ── 季更 ──┐
  行情/估值 ── 周更 ──┼→ 全 A 股预计算 → 入库（DuckDB/PostgreSQL + parquet）
  机构数据 ── 月更 ──┘

用户搜索股票代码 ──→ 从库读取 → 渲染 HTML 长图 ──→ 秒级出报告
```

### 4.3 分层调度频率

| 数据 | 调度频率 | 说明 |
|------|---------|------|
| 财报数据 | **季更** | 跟随财报披露节奏（Q1/Q3 季报、半年报、年报） |
| 行情 / 估值 | **日更 / 周更** | 数据可得、成本低 |
| 机构评级 / 预测 EPS | **周更 / 月更** | 跟随券商研报节奏 |
| 深度跟踪池 | **季更（全量）** | 年报/中报季全量更新，Q1/Q3 轻量 |

### 4.4 数据库选型

全 A 股 5000+ 只 × 多年财报 ≈ **数百万行**，SQLite 在分析查询与并发下捉襟见肘。

| 场景 | 选型 | 理由 |
|------|------|------|
| 本地开发 + 分析 | **DuckDB** | 嵌入式、列式存储、分析查询快、parquet 原生支持、零运维 |
| API 查询层（FastAPI） | **PostgreSQL** | 多用户并发、服务化、生态成熟（规模化迁移目标） |
| 文件层 | **parquet + COS** | 原始数据与中间结果归档，云存储 |
| 云数仓（规模化迁移目标） | **Snowflake / BigQuery** | schema 化表格设计与维护、弹性算力，对齐岗位「现代云数据仓库」要求 |

> 分阶段：当前 DuckDB + parquet 本地（已落地）；后续 PostgreSQL 承接 API 查询，parquet 走 COS 归档。Snowflake/BigQuery 作为规模化后的迁移目标，schema 设计保持与 Postgres 兼容。

### 4.5 数据质量与监控

- 财报数据以公司官方披露为准，逐项校验（模板内「数据校验记录」模块留痕）
- 机构数据标注截至日期与家数
- **数据质量检验**：缺失值 / 异常值 / 口径一致性校验，未通过则告警
- **血缘追踪**：字段级 lineage 标注（源 → 清洗 → 指标），可追溯
- **调度告警**：任务失败 / 延迟告警（Airflow 通知）

> **数据校验方案**（金标准选择、错误分类、三层校验策略、字段白名单）详见 [data-validation.md](data-validation.md)。核心：官方年报 PDF 做金标准，首次全量建基线 + 日常增量守基线 + 定期抽样防漂移。

## 6. 报告层设计

### 6.1 报告生成流程（数据先行）

```
真实财报数据（事实底座，必须拉取）
        ↓
结构化上下文（指标、同比、估值分位、机构评级/预测数据）
        ↓
LLM 仅生成「客观文字段落」（商业模式/投资逻辑/风险，只翻译数据不编观点）
        ↓
模板渲染 → HTML 长图（1080px 宽 × 高度自适应）
        ↓
Playwright 导图（PNG @2x / PDF）
```

**铁律：LLM 只「翻译」不「编数据」** —— 财务数据必须是拉取的真实值，LLM 只负责把数据讲成投研语言，防止幻觉与失真。同理，LLM **不输出本人观点**（无本人目标价、多空、买卖建议）；机构的多空/评级属客观数据，不属 LLM 生成范畴。

**LLM 工程化**（对齐岗位「LLM 层」要求）：

- **结构化输出**：JSON schema 约束 LLM 输出，直接落库与渲染（已落地）
- **客观叙事边界**：LLM 生成的内容严格限定为「对真实数据的客观转述」，主观判断一律不进报告

### 6.2 模板结构（当前 v1.x）

头部 → 商业模式 → 核心财务数据（年度全历史 + 近两年季度 + 业务收入构成）→ 估值与市场 → 投资逻辑 → 风险 → 财务造假检测 → 数据校验 → 免责页脚

- 财务表 / 季度表 / 业务构成为**数据驱动**（加数据即加行）
- 模板由 `scripts/build_valueline.py` 生成
- 「商业模式 / 投资逻辑 / 风险」由 LLM 对真实数据做客观转述，非个人观点

### 6.3 导图

- `scripts/export.py`：Playwright 截图 PNG 长图（@2x 2160px 超清）+ PDF 长页

## 7. 服务层与合规

### 7.1 查询 API（FastAPI）

- **FastAPI** 提供查询 API：按股票代码返回结构化数据（年度/季度/分业务/指标序列/跨股对比）
- 只读 DuckDB mart 层，参数化查询 + 指标白名单防注入（已落地，见 [api.md](api.md)）
- 服务对象是**自己**（决策排雷）与后续可能的分析工具，不预设商业化前端

### 7.2 合规铁律（前置约束，非事后补丁）

- **报告纯客观、零「本人」观点**：不出现本人目标价、本人多空、买卖建议。
- **机构评级 / 预测 EPS（含多空倾向）** 属客观第三方数据，一律标注「第三方机构观点，非本人建议」。
- **主观判断只进私有投研日记**（`journal/`，已 gitignore），不进报告。
- **数据可追溯**：每页附数据校验记录（来源 / 口径 / 校验日期 / 校验人）与免责声明。

> 因为报告只呈现「客观数据 + 第三方机构观点」、不含本人观点，所以天然规避「无牌照发布个股 + 本人目标价 + 本人多空」的非法证券投资咨询风险——这是「去本人观点」定位带来的合规红利。

## 8. AI-Native 数据管道（技术亮点，兼顾简历）

```
Airflow 调度 → 多源抓取 + 文档解析(PDF 金标准) → 清洗入库
        → DuckDB 数仓(raw/mart，含血缘追踪) → 指标计算 + 造假检测
        → LLM 生成报告文本(结构化输出) → 模板渲染 → 导图
        → FastAPI 查询 API
```

- **调度**：Airflow 五阶段 DAG（拉取→交叉校验+造假检测→渲染→数仓→导出），Docker Compose 容器化，端到端跑通 ✅
- **文档解析**：巨潮年报 PDF + pymupdf 表格抽取，金标准交叉校验（容差 <0.1%）✅
- **数仓**：DuckDB 列式数仓（raw/mart 双层 schema 化），PostgreSQL/Snowflake/BigQuery 为规模化迁移目标
- **LLM 应用**：DeepSeek 结构化输出（商业模式/投资逻辑/风险/林奇分类），铁律「只翻译数据不编数」✅
- **后端**：FastAPI 查询 API（7 端点，只读 mart 层，参数化查询 + 白名单防注入）✅
- **云**：已输出《云部署方案设计》[cloud-deployment.md](cloud-deployment.md)——本地 → GCP（Composer/BigQuery/Cloud Run/Secret Manager）的完整映射 + 分阶段迁移路径 + BigQuery DDL（规模化迁移设计已就绪，待实际部署）
- 此架构覆盖岗位「源数据接入 + 文档解析 + 数仓 + 编排监控 + LLM 层 + 后端 + 云」全部七块核心能力
